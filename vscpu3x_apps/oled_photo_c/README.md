This C version is intended to display the same image as `oled_photo` on the SSD1306.
It passes software simulation, but the first hardware test produced noise;
compatibility with the manufactured chip is still under investigation.
The supplied assembly and `.mem` were generated by `vscc_static.c` from
`/home/salih/EE321/VSCPU-Sim/compilers` without editing the generated assembly.
The external compiler and simulator files are unchanged.

From the repository root, rebuild and verify with:

```bash
python3 vscpu3x_apps/oled_photo_c/build.py
```

Use `--sim-dir /path/to/VSCPU-Sim` for another installation. This requires `cc`
and Python 3; the compiler is built in a temporary directory. To run only the
verification, use `python3 vscpu3x_apps/oled_photo_c/verify.py`.

To upload, select codemaker programming mode and run:

```bash
cd vscpu3x_apps/utils
python3 run_test.py oled_photo_c /dev/ttyUSB0 --memclear --skip-address 753
```

Replace the serial port. Keep the core in programming mode through the full
upload readback; switch to run mode only after it passes.
The image occupies addresses 0–726 and the simulated runtime uses RAM through
731, so neither needs 753. Skipping 753 during clearing applies the workaround
that succeeded on hardware with the relocated hand-written photo program;
the C version still needs hardware confirmation with this option.

The GPIO is word address 8254: MOSI bit 0, SCK bit 1, active-low CS bit 2,
and D/C bit 3. This matches `oled_test`. The external `spi_controller.c` and
`VerySimpleCPU_spi.py` decoder use the user's old board mapping. `verify.py` uses
that simulator's instruction engine with a decoder for this wiring and overrides
for the [published ISA v1](http://www.cpu.tc/rtl/): unsigned ADDi, bidirectional
SRL, and 14-bit CPU addresses. The original external simulator files are unchanged.

Verification compares the assembled `.mem` with the simulator's assembly load,
checks every emitted command/data byte against the original photo assembly,
requires a clean halt with CS inactive, and checks runtime memory accesses
against the board's 2048-word RAM plus the GPIO port. The tested build executes
865410 instructions and touches RAM through address 731. Instruction counts
are not CPU clock counts or measured SPI timing.

Compiler constraints relevant to this example:

- Use `vscc_static`, not the current `vscc_stackless`: the latter aliased the
  separate `count` and `pins` locals in the initial test and emitted expression
  stack operations while initializing SP to zero.
- Array initializer storage in the compiler is limited to 256 entries. The
  image therefore contains 256 packed words, unpacked with right shifts and
  masks. A 1024-entry initializer produced corrupt output in the initial test.
- The compiler subset does not support `volatile`. Its generated GPIO stores
  are checked by the execution trace; this source is specific to this compiler.
- The external SPI simulator sign-extends ADDi and disables shifts of 32 or
  more; those behaviors differ from the published ISA. The local verifier now
  uses the published semantics. The C program still passes with those semantics,
  including 14-bit truncation of indirect addresses for stack parameter access.

Reuploading the unchanged original photo fixed the reported hardware symptom.
That points toward programming reliability; it does not establish an SPI timing
fault. The uploader previously exhausted write retries without raising an error.
It now stops on a failed write and requires full image readback before requesting
run mode. Readback proves the programmed contents, not correct CPU execution.
